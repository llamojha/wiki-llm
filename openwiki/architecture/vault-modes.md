# Vault modes: provenance, folders, managed

## Why multiple modes exist

The original design required a declared-spaces manifest
(`_system/structure.json`) before any content could be recognized — good for
AI-curated content with defined categories, bad for "point the portal at a
folder of Markdown notes I already have and have it just work" (the
folder-first vault effort, `specs/folder-first-vault.md`, `plans/021`). Rather
than replace the original layout, the portal now supports both and resolves
which one it's looking at per deployment.

`web/lib/vault-mode.ts` documents the three modes and their resolution order:

- **`provenance`** — the original layout. Documents live under `generated/`,
  `authored/`, or the per-user `users/<id>/…` mirrors; spaces are declared in
  `_system/structure.json`. This is what the AI curation pipeline produces
  (see [Curate pipeline](../workflows/curate-pipeline.md)).
- **`folders`** — the zero-config on-ramp. Any `.md`/`.html` under the vault
  (outside `_system/`) is a document, and the top-level folders *are* the
  spaces.
- **`managed`** — the metadata-derived evolution (`plans/027`,
  `specs/managed-mode.md`). Recognizes the same keys as `folders`, but the
  page tree comes from a frontmatter `parent_id` edge (falling back to the
  key path when absent), so re-parenting a page is a one-file metadata edit
  rather than an object move.

Resolution order (highest wins):
1. Explicit `VAULT_MODE=folders|provenance|managed` env var.
2. Sniff — `managed` if the `_system/managed.json` marker exists (managed
   recognizes the same keys as folders, so only this explicit marker —
   written by reconcile/migration — distinguishes them); else `provenance`
   if `_system/structure.json` exists, or any `generated/`/`authored/`
   document is present, or a `users/<id>/(generated|authored)/` key exists
   (covers the old personal-editor-only vault shape, which has no root
   structure.json or shared docs but is still provenance). Otherwise
   `folders`.
3. Default `folders`.

The sniff runs once and is cached (`ensureVaultMode()`); the synchronous
`vaultMode()` getter returns the cached value, or `provenance` as a
conservative fallback before the first resolution completes. Under the S3
mock (`MOCK_S3=1`, used by unit/e2e tests) the mode is re-sniffed on every
call instead of cached, since the in-memory store is reseeded between test
cases and a stale cached mode would leak across cases with different vault
shapes.

## Provenance without a folder: the `origin` frontmatter field

Folders mode has no `generated/`/`authored/` root to key off, so provenance
(was this page written by a person or generated by AI?) moved into
frontmatter. `web/lib/origin.ts` defines the vocabulary:

```
authored | generated | uploaded | imported
```

`readOrigin(frontmatter)` resolves precedence: canonical `origin` field →
legacy `source_type` field (for pages written before this existed) → default
`authored`. Provenance mode's `source_type: personal` maps to `authored`,
since folders mode has no personal tree concept. A page with no provenance
frontmatter at all is treated as human-authored (`DEFAULT_ORIGIN`).

This means the same conceptual fact ("is this AI-generated") is represented
two different ways depending on vault mode — a folder location in
provenance mode, a frontmatter value in folders mode — and any code that
needs to answer "is this page AI-generated" for both modes must check both
paths. `web/lib/search.ts`'s `entryForKey` does this: it prefers
`data.origin` when present, falling back to path-based inference otherwise.

## Path and key rules

`web/lib/vault-paths.ts` centralizes what counts as a "document key" for
each mode (`isDocumentKey`), the `.md`/`.html` extension rules
(`hasDocExtension`, `isHtmlKey`), and folder-path normalization
(`normalizeFolderPath`, added for the folders-mode curate pipeline's
source/destination folder inputs — see
[Curate pipeline](../workflows/curate-pipeline.md)). `_system/` is the one
universally reserved prefix in both modes — it holds indexes, job state,
manifests, and logs, never user-visible documents.

## Things to watch when editing

- Any new code that lists/filters vault content must branch on `vaultMode()`
  (after `await ensureVaultMode()`) rather than assuming provenance's
  `generated/`/`authored/` layout — folders-mode vaults have neither.
  `web/lib/folders.ts` (tree building) and `web/lib/search.ts` (index
  building) are the reference implementations of this branch.
- Do not introduce a third hidden-subtree convention (e.g. a `_canopy/`
  folder) for folders-mode metadata — the explicit maintainer decision
  (`plans/026`) is that provenance lives in frontmatter, not in magic paths,
  to keep folders mode's promise of "any folder of Markdown just works"
  intact.
- Managed mode — the third mode with a metadata-derived tree instead of
  either folder scanning or a structure.json manifest — **is implemented**
  (`plans/027`, design record `specs/managed-mode.md`). The tree is
  assembled from frontmatter `parent_id` (`web/lib/managed-tree.ts`), with
  `POST /api/docs/reparent` editing the edge and
  `POST /api/managed/reconcile` rebuilding page records. A vault is promoted
  by the `_system/managed.json` marker.
